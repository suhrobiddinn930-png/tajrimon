# Repository Guidelines

## Project Structure & Module Organization

The Flutter client uses Supabase directly for email authentication and its own profile/preferences.
Room admission, billing allowance and audio all pass through FastAPI. The API verifies tokens through
Supabase Auth, then uses trusted service-role database access with explicit membership checks.
RLS is a second boundary for direct mobile database access. Read `docs/ARCHITECTURE.md` before
changing either path; server service-role queries bypass RLS.

Audio translation is a turn-based server adapter, not a WebRTC or direct Realtime client.
The in-memory hub and one-use tickets require one worker and one replica. No audio or transcript
table exists. Provider mocks belong only in `backend/tests`. Mobile runners are generated by
`scripts/bootstrap_mobile.py`, which refuses to overwrite existing Android/iOS projects.

## Build, Test, and Development Commands

- Install backend tools: `python -m pip install -r backend/requirements-dev.txt`.
- Start locally: `python -m uvicorn backend.api.app:app --env-file .env --workers 1 --ws-max-size 500000 --ws-max-queue 1 --no-access-log`.
- Offline/API tests: `python -m pytest -q -m 'not integration'`.
- Single test module: `python -m pytest -q backend/tests/test_controls.py`.
- Database tests: set `TEST_DATABASE_URL` to a disposable localhost Supabase/PostgreSQL database
  with migrations applied, then `python -m pytest -q -m integration`.
- Isolated PostgreSQL alternative: `python scripts/test_postgres.py --bin PATH_TO_POSTGRES_BIN`.
- Lint/format: `ruff check backend scripts` and `ruff format --check backend scripts`.
- Mobile: generate runners, then run `flutter pub get`, `flutter analyze`, and `flutter test` inside `mobile`.

## Coding Style & Testing Guidelines

Python targets 3.12, a 100-character line limit and Ruff rules E/F/I/B/UP with B008 exempted.
Flutter uses `flutter_lints`; `avoid_print` is an analyzer error. Format with `dart format lib test`.
The pytest integration marker distinguishes real PostgreSQL tests from HTTP/provider boundary stubs.
Database tests use authenticated roles and transaction rollback; the concurrency test commits only
its explicit fixture IDs and deletes those IDs afterward. Check `docs/TEST_RESULTS.md` before
claiming provider, Supabase or mobile validation. No commit-message convention is established yet.
